=== what was fixed (self-audit of the stage-2 code) ===
1. The incarnation was read BEFORE the applying section on the forwarded path, so a delivery admitted against the
   previous copy could be written onto the new one; the WAL path did not check it at all, although a stream is
   long-lived and outlives a restore. Both now check inside the section that holds the DB handle alive.
2. The forwarded path wrote data without maintaining curr_items at all, and the WAL path probed existence per
   change, so a key created twice (or created and deleted) inside one batch was counted twice. Both now use an
   in-batch existence overlay, alongside the ordering overlay.
3. An EMPTY batch claimed the position base_seq, i.e. a sequence it never carried.
4. collect_tombstones() and get_repl_tombstones() touched the DB handle without the whole-lock, which is what a
   snapshot swap, a hard reset or a close takes in write mode before destroying it — a use-after-free window
   against exactly the operations this design adds.

=== new tests ===
test_apply_rule_metadata_only_batch_advances_position     pass   a batch of metadata-family entries applies no data, yet its entries are numbered and the position moves past them
test_apply_rule_empty_batch_does_not_move_position        pass   an empty batch covers no sequence and claims none
test_apply_rule_curr_items_matches_real_key_count         pass   curr_items equals an independent iteration after both paths, including a key written twice and a key created-then-deleted in ONE batch
test_apply_rule_incarnation_checked_against_the_current_copy  pass   a delivery for the previous copy is refused on both paths after the copy was replaced
test_apply_rule_concurrent_forwarded_and_wal              pass   4 threads of forwarded changes against the same keys while the applier delivers its own batches: the count never drifts from the key space, the position moves only by the applier, and every contended key ends at the highest label offered
