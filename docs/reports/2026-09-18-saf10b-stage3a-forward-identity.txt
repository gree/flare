=== what was wired ===
* storage::entry gains repl_tag, parsed from the wire as a trailing "rl=<epoch>/<label>" token. It is recognised
  before the option parser, which rejects unknown words — so a node that does not understand it is never sent it.
* queue_proxy_write stamps the tag from the source epoch and the label captured inside the key's critical section,
  but ONLY when cluster::get_repl_identity_forward() is on.
* op_set and op_delete apply a tagged, proxied change through storage::apply_identified_change() — the common rule —
  and fall back to the previous path when the backend reports it unsupported.
* Outcome mapping for the source: applied/skipped -> success (the destination is not behind, so no drop is counted
  and no repair is requested), refused -> SERVER_ERROR (the destination is not following our history and the
  source's retry and drop accounting must surface it), error -> SERVER_ERROR.
* flared gains the runtime option repl-identity-forward (default FALSE, dynamic). It must stay off until every node
  understands the tag: an older node would reject the request outright and every forwarded write would be dropped.

=== a build hygiene note, repeated ===
Adding a member to storage::entry (a header shared by the library and the test modules, which statically embed
libflare objects) produced the same stale-link symptom as in stage 2: a vector of entries appearing one element
short, counters reading as garbage, and one test aborting with no message. `make -C test/lib clean` before
rebuilding is required after ANY header change here. Two working hypotheses were chased before this was identified
(a corruption-latch regression and a reaper regression); both were artefacts, and the library behaved correctly
throughout.
